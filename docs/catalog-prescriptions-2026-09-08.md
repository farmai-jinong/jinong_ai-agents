# 카탈로그 처방으로 용어 후보정이 사전 등록 기준을 넘는다 (2026-09-08, 같은 날 후속)

> **정정 (같은 날 3편)**: 이 문서의 base 좌표(`deploy-base-k10-jinong`)는 정답 대본에서 뽑은 bias 목록을
> 프롬프트에 넣은 **오라클 팔**이었다. 진짜 pass-1 좌표에서 base 용어 recall 은 .84 가 아니라 .3526 이다.
> 표본을 421통화·12,596발화로 늘리며 드러났고, 정본은 [`stt-term-fix-scale-2026-09-08.md`](./stt-term-fix-scale-2026-09-08.md) 다.
> 아래 수치는 그 좌표 위에서만 유효하다.

[전편](./stt-term-fix-calls-2026-09-08.md)에서 실통화 84통화 재측정은 **FAIL** 이었다 — 용어는 복구되는데
(exact .8071→.9143) 치환 precision(lenient) 이 .8298 로 사전 등록 .90 에 못 미쳤다. 그리고 그 오탐 8건 중
**6건이 환각이 아니라 카탈로그 문제**였다. 그래서 카탈로그·가드를 변수로 두고 다시 쟀다.

## 1. 하네스 — `voice_eval/term_fix/tune.py`

`jinong_gpu` stt-041 의 처방 비교표와 같은 구조다. 2단으로 나눈 것이 핵심이다.

1. **스크리닝 (LLM 0콜, 84통화 수 초)** — 캐시된 LLM 제안은 그대로 두고 카탈로그·가드만 갈아 끼워 재적용·재채점한다.
   "`팜한농포리캡탄`의 canonical 을 `포리캡탄`으로 바꾸면 그 치환이 FP 에서 TP 로 도는가" 에 즉답한다.
2. **확정 (`--confirm`, LLM 재호출)** — 카탈로그는 프롬프트에 통째로 들어가므로 **바뀌면 제안 자체가 달라진다.**
   스크리닝은 "LLM 이 같은 제안을 냈다면" 의 반사실이라, 채택 후보는 반드시 다시 불러 재야 한다.

```bash
python -m app.agents.voice_eval.term_fix.tune \
  --run out/term-fix-calls-base --fixtures out/term-fix-calls/fixtures/base --min-confidence 0.9 \
  --out out/term-fix-tune [--confirm ALL] [--keep-cache]
```

| id | 처방 |
|---|---|
| `R1` | 농약상표의 **회사명 접두 87건**을 떼어 canonical 로(+ 맨 표기 ≥3자는 표제로도) — stt-041 처방 ①(법인 접두)이 손대지 않은 나머지 절반 |
| `R2` | 가드: **원문이 카탈로그의 다른 용어면 거부** — 멀쩡히 알아들은 상표를 닮은 표제로 바꾸는 것(`마세트`→`마세트300`) |
| `R3` | **카탈로그 구멍 보강 9건**(`catalog_gaps.tsv`) — 실통화에서 발화됐는데 표제에 없어 모델이 닮은 표제로 끌려가던 말 |
| `ALL` | 셋 다 |

## 4. 이득이 어디서 왔나 (확정 팔의 제안 위에 각 처방을 다시 적용)

| 처방 | TP/이형/FP | lenient |
|---|---|---:|
| R0 (원래 카탈로그·가드로 채점) | 37/5/4 | .9130 |
| R2 | 37/5/3 | .9333 |
| R3 | 46/5/4 | .9273 |
| ALL | 48/5/3 | .9464 |

**가장 큰 몫은 프롬프트다.** 같은 제안 집합을 원래 카탈로그로 채점해도 이미 .9130 이다 — 즉 구멍 9건을
프롬프트에 넣은 것만으로 LLM 이 닮은 표제로 끌려가기를 그만뒀다. R3 은 그 제안을 승인해 TP 를 37→46 으로
올리고, R2 는 남은 오탐을 하나 더 깎는다. **카탈로그는 사전이 아니라 프롬프트의 일부다.**

## 6. 반영한 것 · 반영하지 않은 것

**agents 런타임(이 레포)** — 카탈로그 파일은 여전히 경로로만 읽고 복사하지 않는다. 처방은 **로더가** 적용한다:

- `catalog.load_catalog(company_prefix=True, gaps=...)` — 회사명 접두 재작성은 카탈로그 안의 `company` 표기로
  스스로 계산하므로 데이터를 들여오지 않는다. 구멍 9건만 `voice_eval/term_fix/catalog_gaps.tsv` 로 들고 있다
  (사람이 검수한 목록 + 근거 발화). `jinong_gpu` 카탈로그가 이들을 받으면 **이 파일은 지운다.**
- `apply_corrections(reject_catalog_originals=True)` — 순수 가드.
- 노브 `TERM_FIX_COMPANY_PREFIX` / `TERM_FIX_GAPS_PATH` / `TERM_FIX_REJECT_CATALOG_ORIGINALS` (기본 켜짐).
  **`TERM_FIX_ENABLED` 는 여전히 off** — 켤지는 일지 품질(judge) 쪽 근거가 따로 필요하다(§7).

**`jinong_gpu`** — 스크립트와 근거만 넣었고 **라이브 카탈로그는 건드리지 않았다.**
`stt-serve/catalog/strip_company_prefix.py`(기본은 canonical 재작성만, `--add-bare` 는 별도 플래그)와
`gaps_jinong_call_2026-09-08.tsv`. 이유: 그쪽에서 카탈로그는 **리트리버의 매칭 표면**이기도 해서 표제를 늘리면
`--domain-fuzzy-min-jamo 6` 대역(stt-041 이 주입 precision 37% 로 잰 그 대역)이 움직인다. 우리 좌표에서는
표제가 프롬프트 목록일 뿐이라 그 위험이 없다. **2,354행 페어드 게이트는 그쪽 규약이고 그쪽 몫이다.**

**게이트웨이** — 바꿀 것이 없다. 벤더 사본 md5 는 GPU 와 같고(`6bbfc857`), 배포는 SG 차단으로 대기 중이다.

## 7. 다음

- 지금 열려 있는 질문은 STT 지표가 아니라 **일지 품질**이다. 용어 exact .8071→.9143 이 방제이력·약제 추출을
  얼마나 바꾸는지는 judge 축에서만 보인다(5건 on/off 에서 coverage +0.4~0.8). `TERM_FIX_ENABLED` 를 켜는
  결정은 그 측정 뒤에.
- `jinong_gpu` 가 처방을 받아 카탈로그가 바뀌면 로더 노브를 끄고 파일만 따라간다. 그때 `catalog_gaps.tsv` 삭제.
- 랭킹 오탐(`톤풀→콩풀`, 정답 `스토풀`은 표제에 있음)은 프롬프트가 아니라 후보 제시 방식의 문제다 — 카탈로그를
  통째로 넣는 대신 발음 근접 후보를 추려 주는 갈래인데, 이번 판정에 필요하지 않아 열지 않았다.
