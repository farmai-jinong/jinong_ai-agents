# STT 를 CPU 로 서빙할 수 있나 — 짧은 실측 (2026-09-08)

**결론: 된다. 실시간의 1.5배 속도로 돈다(RTF 0.65).** 품질 손실도 없다. 다만 지금 운영 좌표보다 **24배 느리고**,
지금 코드로는 **승격 체크포인트를 못 쓴다**(base 고정).

## 재본 것

같은 오디오 25발화(총 73.6초, 평균 2.9초), 같은 클라이언트, 동시성 1, `diarize=false`(순수 ASR).
`jinong_gpu` 박스에서 여유 포트에 임시로 띄워 쟀다. CPU 팔은 `OMP_NUM_THREADS=16` 으로 묶어 학습 잡을
밀어내지 않게 했다.

| 팔 | 장치 | 엔진 | 모델 | 지연/발화 | RTF | 실시간 배수 | CER(공백제거) |
|---|---|---|---|---:|---:|---:|---:|
| A | **CPU** | FunASR | base | **1,907 ms** | **0.65** | 1.5× | .0979 |
| B | GPU | FunASR | base | 464 ms | 0.16 | 6.3× | .1005 |
| C | GPU | vLLM | **승격**(운영) | **80 ms** | **0.03** | 36.7× | **.0661** |

- RTF = 처리시간 ÷ 오디오 길이. 1.0 미만이면 실시간보다 빠르다.
- 실패 0건.

## 읽는 법

**① CPU 서빙은 실제로 가능하다.** RTF 0.65 는 10분짜리 통화를 6.5분에 처리한다는 뜻이다. 배치 처리(통화가
끝난 뒤 전사)라면 충분히 쓸 수 있는 수치다. 실시간 스트리밍은 여유가 1.5배뿐이라 위태롭다.

**② CPU 라서 품질이 나빠지지는 않는다.** A(.0979) vs B(.1005) — 같은 모델이면 장치가 CER 을 바꾸지 않는다
(차이는 25발화 표본의 수치 잡음). **C 가 좋은 건 GPU 라서가 아니라 승격 모델이라서다.**

**③ 장치 효과는 4.1배** (A/B, 엔진·모델 고정). 운영 대비 24배(A/C)인 것은 장치(4.1배)와 엔진·모델(5.8배)이
곱해진 결과다.

**④ 지금 코드로는 CPU 에서 승격 모델을 못 쓴다.** CPU 경로는 FunASR 을 타는데, FunASR `AutoModel` 은
레지스트리 키로만 모델을 찾아 로컬 FT 디렉터리를 `"not registered"` 로 거부한다(오늘 `:8102` 를 고치면서
확인한 그 제약이 CPU 에도 그대로 적용된다). CPU 에서 승격 모델을 쓰려면 FunASR 말고 다른 로더가 필요하다
(transformers 직접 적재 또는 vLLM CPU 백엔드) — **미검증**.

## 자원

| | CPU 팔 |
|---|---|
| RAM | **4.8 GB** (RSS) |
| 스레드 | 16(연산 제한) / 프로세스 73 |
| GPU | **0** (미사용 확인) |
| 기동 시간 | ~2분 (FunASR 레지스트리 스캔 포함) |

72스레드 박스에서 16스레드씩 쪼개면 동시 4통화 정도가 상한이다.

## 남는 것 · 주의

- **운영 박스(AWS) CPU 사양은 미확인.** 여기서 접속이 막혀(7022 refused) 못 쟀다. 위 숫자는 AMD EPYC 9365
  (36코어/72스레드) 기준이라, 코어가 적은 박스에서는 RTF 가 1.0 을 넘어 실시간을 못 따라갈 수 있다.
  **CPU 서빙을 실제로 검토한다면 그 박스에서 같은 25발화로 다시 재는 게 먼저다.**
- 이 측정은 **ASR 만**이다. 화자분리 경로는 pyannote(`:8104`)가 따로 필요하고 그건 지금 GPU 에 있다.
  "GPU 없이 운영"을 보려면 pyannote CPU 도 따로 재야 한다.
- 표본 25발화(74초)는 순위를 가르기엔 충분하지만 CER 절대값을 논할 크기는 아니다.

# 부록: CPU 서빙에 필요한 자원과 AWS 비용 (2026-09-08 추가)

## 1. 필요한 자원 — **4 vCPU · 8 GB 면 충분하다**

스레드를 늘려도 거의 안 빨라진다. 같은 15발화를 스레드 수만 바꿔 재봤다:

| 스레드 | 지연/발화 | RTF | 실시간 배수 | 최대 RSS |
|---:|---:|---:|---:|---:|
| 4 | 2,415 ms | 0.73 | 1.4× | 5.0 GB |
| 8 | 2,107 ms | 0.64 | 1.6× | 5.0 GB |
| 16 | 2,069 ms | 0.63 | 1.6× | 5.0 GB |
| 32 | 2,570 ms | **0.78** | 1.3× | 5.0 GB |

- **4 → 16 스레드(4배)로 RTF 0.73 → 0.63, 겨우 16% 개선.** 32 에서는 경합으로 오히려 나빠진다.
  1.7B 자기회귀 디코딩은 토큰마다 의존이 걸려 코어를 더 줘도 못 쓴다 — **코어를 사는 건 돈 낭비다.**
- 메모리는 스레드 수와 무관하게 **최대 RSS 5.0 GB 고정**. 컨테이너는 8 GB 면 안전하다(6 GB 는 빠듯).
- 기동 ~2분(FunASR 레지스트리 스캔 포함), GPU 0.
- 측정 박스가 load 20+ 로 붐비는 상태였다 — 한가한 전용 박스면 조금 더 나올 수 있다.

**권장 컨테이너 규격: 4 vCPU / 8 GB.**

## 2. AWS 비용 (ap-northeast-2 서울, 온디맨드 Linux, 730시간/월)

단가는 AWS 가격 엔드포인트에서 직접 받은 값이다(`b0.p.awsstatic.com/pricing/2.0/…/Asia Pacific (Seoul)`).

| 인스턴스 | 규격 | 시간당 | **월** | 최대 처리 | 통화당(100%) | 통화당(30% 가동) |
|---|---|---:|---:|---:|---:|---:|
| **c7i.xlarge** | 4 vCPU / 8 GB | $0.2016 | **$147** | 54,400 통화/월 | $0.0027 | $0.0090 |
| c7g.xlarge (ARM) | 4 vCPU / 8 GB | $0.1632 | **$119** | 54,400 | $0.0022 | $0.0073 |
| m7i.xlarge | 4 vCPU / 16 GB | $0.2478 | $181 | 54,400 | $0.0033 | $0.0111 |
| c7i.2xlarge | 8 vCPU / 16 GB | $0.4032 | $294 | 62,000 | $0.0047 | $0.0158 |
| *(참고)* g4dn.xlarge | T4 GPU | $0.6470 | $472 | 1,320,000 | $0.00036 | — |
| *(참고)* g6.xlarge | L4 GPU | $0.9896 | $722 | 1,320,000 | $0.00055 | — |

- 처리량 환산: 통화당 전사 대상 오디오 **66초**(화자분리 경로는 턴 조각만 전사한다 — `jinong-call`
  93통화 2,354세그먼트 1.71h 기준). RTF 0.73 → 컨테이너 하나가 월 1,000시간 오디오.
- **c7i.2xlarge 는 사지 마라** — vCPU 를 2배 주고 14% 처리량을 얻으려고 2배를 낸다.
- **Graviton(c7g)이 19% 싸지만 ARM 에서 이 스택(FunASR·torch·qwen-asr)이 도는지는 미검증**이다.
- Fargate 는 서울 단가를 공개 엔드포인트에서 못 받았다. us-east-1 기준(vCPU $0.0405/h, GB $0.00444/h)으로
  4 vCPU+8 GB = 약 $0.198/h ≈ **$144/월**로 c7i.xlarge 와 비슷하고, 서울은 이보다 높다.

## 3. 판단에 필요한 세 가지

**① 지금은 GPU 비용이 0 이다.** 서빙은 사내 GPU 박스에서 돈다. CPU 로 옮기는 건 절감이 아니라
**월 $119~181 의 신규 비용**을 만드는 선택이다. 이유가 "GPU 비용 절감" 이면 성립하지 않고,
"사내 박스 의존을 끊는다 / AWS 안에서 자급한다" 면 성립한다.

**② 품질이 떨어진다.** CPU 경로는 FunASR 이라 승격 체크포인트를 못 쓴다(§본문 ④). 같은 25발화에서
CER **.0661(운영) → .0979(CPU+base)**, 상대 +48%. 이건 장치 탓이 아니라 모델 탓이라, CPU 에서도 승격
모델을 올릴 수 있으면(transformers 직접 적재 등, 미검증) 사라질 격차다. **CPU 검토의 진짜 선행 과제는
비용이 아니라 이 로더다.**

**③ 이 값은 ASR 만이다.** 화자분리(pyannote)가 따로 필요하고 지금 GPU 에 있다. "AWS 컨테이너 하나로
STT 를 자급" 하려면 pyannote CPU 도 재야 하고, 그만큼 vCPU·메모리·비용이 더 붙는다.

## 4. 남은 확인

- 운영 박스(AWS) CPU 사양 — 접속이 막혀 미확인. 코어가 적으면 RTF 가 1.0 을 넘을 수 있다.
- ARM(Graviton) 동작 여부 — 19% 절감이 걸려 있다.
- CPU 에서 승격 모델 적재 — 품질 격차 전부가 여기 달렸다.
- pyannote CPU RTF.

# 부록 2: 후처리(`:8105`)까지 포함하면 (2026-09-08 추가)

**본문과 부록 1 의 수치는 순수 ASR 만이다** — 벤치가 `diarize=false` 로 ASR 서버를 직접 때렸기 때문에
`:8105` 후처리 레이어(용어 검색 + 2패스 재전사 + 병합)도, pyannote 화자분리도 들어가 있지 않다.
후처리를 CPU ASR 위에 그대로 얹어(`qwen_ctx_server` 를 CPU 백엔드로, 운영과 같은 노브) 다시 쟀다.

| 구성 | 지연/발화 | RTF | 실시간 배수 | CER | 2패스율 |
|---|---:|---:|---:|---:|---:|
| CPU · ASR 만 | 2,396 ms | 0.73 | 1.4× | .0744 | 0/15 |
| **CPU · ASR + 후처리** | **2,785 ms** | **0.84** | **1.2×** | .0744 | 3/15 |
| GPU · ASR 만 (운영) | 68 ms | 0.02 | 48.2× | .0702 | 0/15 |
| **GPU · ASR + 후처리 (운영)** | **313 ms** | **0.09** | **10.6×** | .0702 | 3/15 |

- **후처리 비용은 어느 쪽에서나 절대값 ~250~390 ms 로 비슷하다.** 검색이 카탈로그 5.7만 항목을 자모로 훑는
  **CPU 작업**이라 백엔드와 무관하다(`:8105` 응답의 `retrieval_s` ≈ 0.20초). 그래서 GPU 쪽은 상대 비용이
  크고(0.02 → 0.09, 4.6배) CPU 쪽은 작다(0.73 → 0.84, +15%).
- **CER 은 후처리 유무로 안 바뀐다**(.0744 → .0744, .0702 → .0702). stt-041 의 "실현 이득 ≈ 0" 과 일치한다.
- 2패스가 걸린 건 15발화 중 3건. 나머지는 검색 결과가 비어 1패스로 통과한다(K=0 폴스루).

### 용량·비용 재계산 (후처리 포함)

| 구성 | RTF | 월 처리 오디오 | 최대 통화/월 | 월 비용 | 통화당(30% 가동) |
|---|---:|---:|---:|---:|---:|
| c7i.xlarge · ASR 만 | 0.73 | 1,000 h | 54,400 | $147 | $0.0090 |
| **c7i.xlarge · ASR+후처리** | **0.84** | **869 h** | **47,300** | $147 | **$0.0104** |
| c7g.xlarge · ASR+후처리 (ARM) | 0.84 | 869 h | 47,300 | $119 | $0.0084 |
| *(참고)* g4dn.xlarge · ASR+후처리 | 0.09 | 8,111 h | 441,000 | $472 | — |

후처리를 넣어도 **컨테이너 하나가 월 4.7만 통화**를 처리한다 — 결론은 안 바뀌지만 실시간 여유가
1.4배 → **1.2배**로 줄어든다. 실시간 스트리밍에는 사실상 여유가 없다.

### 아직 안 들어간 것 — pyannote

위 수치에도 **화자분리는 빠져 있다.** agents 운영 경로는 `diarize=true` 라 pyannote(`:8104`)가 통화 전체를
한 번 훑고, 그 뒤에 턴 조각마다 ASR 이 돈다. pyannote 는 지금 GPU 에 있고 CPU RTF 를 재지 않았다.
**"AWS 컨테이너 하나로 STT 자급"의 마지막 미지수가 이것이다.**

### 측정 메모 (내 실수 하나)

첫 측정에서 GPU 후처리 팔의 CER 이 **1.3719** 로 나왔는데, 이건 품질 문제가 아니라 **내 계측 오류**였다.
`:8105` 를 직접 때리면 `:8100` 의 원시 디코드 접두사(`language Korean<asr_text>`)가 그대로 남는데,
그걸 벗기는 것은 **게이트웨이의 책임으로 설계돼 있다**(`jinong_ai-gateway/app/upstream.py`:
*"Qwen3-ASR's `language Korean<asr_text>` decode leak — is the gateway's job"*). 게이트웨이를 건너뛴
직타라서 생긴 것이고, 운영 게이트웨이로는 plain·diarize 양쪽 모두 깨끗하게 나온다(실측 확인).
위 표는 그 마커를 게이트웨이와 같은 규칙으로 벗기고 다시 잰 값이다.
