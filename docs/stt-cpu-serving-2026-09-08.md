# STT 를 CPU 로 서빙할 수 있나 — 짧은 실측 (2026-09-08)

**결론: 된다. 실시간의 1.5배 속도로 돈다(RTF 0.65).** 품질 손실도 없다. 다만 지금 운영 좌표보다 **24배 느리고**,
지금 코드로는 **승격 체크포인트를 못 쓴다**(base 고정).

## 재본 것

같은 오디오 25발화(총 73.6초, 평균 2.9초), 같은 클라이언트, 동시성 1, `diarize=false`(순수 ASR).
`jinong_gpu` 박스에서 여유 포트에 임시로 띄워 쟀다. CPU 팔은 `OMP_NUM_THREADS=16` 으로 묶어 학습 잡을
밀어내지 않게 했다.

| 팔 | 장치 | 엔진 | 모델 | 지연/발화 | RTF | 실시간 배수 | CER(공백제거) |
|---|---|---|---|---:|---:|---:|---:|
| A | **CPU** | FunASR | base | **1,907 ms** | **0.65** | 1.5× | .0979 |
| B | GPU | FunASR | base | 464 ms | 0.16 | 6.3× | .1005 |
| C | GPU | vLLM | **승격**(운영) | **80 ms** | **0.03** | 36.7× | **.0661** |

- RTF = 처리시간 ÷ 오디오 길이. 1.0 미만이면 실시간보다 빠르다.
- 실패 0건.

## 읽는 법

**① CPU 서빙은 실제로 가능하다.** RTF 0.65 는 10분짜리 통화를 6.5분에 처리한다는 뜻이다. 배치 처리(통화가
끝난 뒤 전사)라면 충분히 쓸 수 있는 수치다. 실시간 스트리밍은 여유가 1.5배뿐이라 위태롭다.

**② CPU 라서 품질이 나빠지지는 않는다.** A(.0979) vs B(.1005) — 같은 모델이면 장치가 CER 을 바꾸지 않는다
(차이는 25발화 표본의 수치 잡음). **C 가 좋은 건 GPU 라서가 아니라 승격 모델이라서다.**

**③ 장치 효과는 4.1배** (A/B, 엔진·모델 고정). 운영 대비 24배(A/C)인 것은 장치(4.1배)와 엔진·모델(5.8배)이
곱해진 결과다.

**④ 지금 코드로는 CPU 에서 승격 모델을 못 쓴다.** CPU 경로는 FunASR 을 타는데, FunASR `AutoModel` 은
레지스트리 키로만 모델을 찾아 로컬 FT 디렉터리를 `"not registered"` 로 거부한다(오늘 `:8102` 를 고치면서
확인한 그 제약이 CPU 에도 그대로 적용된다). CPU 에서 승격 모델을 쓰려면 FunASR 말고 다른 로더가 필요하다
(transformers 직접 적재 또는 vLLM CPU 백엔드) — **미검증**.

## 자원

| | CPU 팔 |
|---|---|
| RAM | **4.8 GB** (RSS) |
| 스레드 | 16(연산 제한) / 프로세스 73 |
| GPU | **0** (미사용 확인) |
| 기동 시간 | ~2분 (FunASR 레지스트리 스캔 포함) |

72스레드 박스에서 16스레드씩 쪼개면 동시 4통화 정도가 상한이다.

## 남는 것 · 주의

- **운영 박스(AWS) CPU 사양은 미확인.** 여기서 접속이 막혀(7022 refused) 못 쟀다. 위 숫자는 AMD EPYC 9365
  (36코어/72스레드) 기준이라, 코어가 적은 박스에서는 RTF 가 1.0 을 넘어 실시간을 못 따라갈 수 있다.
  **CPU 서빙을 실제로 검토한다면 그 박스에서 같은 25발화로 다시 재는 게 먼저다.**
- 이 측정은 **ASR 만**이다. 화자분리 경로는 pyannote(`:8104`)가 따로 필요하고 그건 지금 GPU 에 있다.
  "GPU 없이 운영"을 보려면 pyannote CPU 도 따로 재야 한다.
- 표본 25발화(74초)는 순위를 가르기엔 충분하지만 CER 절대값을 논할 크기는 아니다.
