# 보이스톡 영농일지 생성 — STT·생성 품질 리포트 (2026-08-27)

팜스올 보이스톡(농가↔컨설턴트 통화) 녹음을 STT로 전사하고 LLM 파이프라인으로 작물별 영농일지
초안을 만드는 에이전트(`jinong_ai-agents`)의 실녹음 평가 결과다. 이 문서 하나로 측정 방법,
STT 성능, 생성 성능, 이번에 무엇을 고쳐 점수가 올랐는지, 남은 한계까지 파악할 수 있게 썼다.

## 한눈에 보는 핵심 숫자 (비개발자·대외 보고용)

정답(사람이 만든 완성 일지) 대비 **절대 성능**이다. 비교 기준 없이 그대로 인용할 수 있다.

| 숫자 | 항목 | 뜻 |
|---|---|---|
| **90%** | 영농일지 종합 정확도 | 사람이 작성한 정답 일지와 문항별 대조한 종합 품질 (0.9033/1.0) |
| **95%** | 핵심 용어 음성 인식률 | 농약 상표명·병해충 이름 등 일지를 좌우하는 단어 기준. 20개 중 놓친 건 1개 |
| **9/10** | 핵심 사실 기록률 | 기록해야 할 작업·병해충·투입 제품 40건 중 36건이 일지에 담김 (90%) |
| **100%** | 발생단계·화자 구분 | 병해충 발생 정도 표기 전부 일치, 농가/컨설턴트 구분 5통화 전부 정확 |
| **0건** | 잡담 유입 | 일지와 무관한 사담이 기록에 섞인 사례 없음 (chatter 5.0/5.0) |

**개선 여지** — 남은 감점의 60%가 "세부 서술 누락" 한 유형에 몰려 있고, 이를 해소할 구조 개선
후보 3건이 이미 식별돼 있다(§5). 평가·개선 루프가 자동화돼 있어 품질을 떨어뜨리는 변경은 자동
기각되며(8회 전부 기각 실적), 같은 절차로 이번에 0.78 → 0.90을 만들었다 — 개선은 일회성이 아니라
반복 가능한 절차다.

| 지표 | 값 | 비고 |
|---|---|---|
| **종합점수** (0~1) | **0.9033** | 기준 0.7800 → ▲0.123 |
| 발생단계 정확도 | 1.000 | 0.667 → ▲0.333 |
| 기대추출 재현율 | 0.900 | 전 구간 유지 (하락 없음) |
| STT 핵심어 인식률 | 0.950 | CER 0.131 |

> 종합점수 = judge 축평균(50%) + 기대추출 재현율(30%) + 발생단계 정확도(20%).
> 자가 개선 루프의 목적함수와 동일한 정의다.

## 1. 무엇을 어떻게 측정했나

평가 대상은 **실녹음 5건**(딸기 4건, 토마토 1건 — 대본 낭독, 케이스당 약 3분)이다. 각 케이스는
대본·정답 일지·기대 추출 목록이 리포지토리에 커밋돼 있고(`tests/agents/testcases/voice/`),
녹음 파일만 외부에 둔다. 파이프라인 경로는 운영과 동일하다.

- **STT** — ⑥ 게이트웨이의 화자분리(diarize) 전사. GPU 서빙 직접 호출 없음.
- **생성** — LangGraph 파이프라인, LLM은 Vertex AI `gemini-3.5-flash`.
  사실 추출 → farmos 표준코드 매핑 → 섹션 렌더 → 검수 패스.
- **채점** — 별도 모델 `gemini-2.5-pro`가 정답 일지와 대조해 6개 축
  (coverage·faithfulness·classification·severity·chatter·format)을 1~5점으로 채점.
  자기채점 편향을 피하려고 생성 모델과 분리했고, 확정 판정은 **3회 반복 채점**으로 했다.

여기에 LLM과 무관한 **결정적 지표** 두 개를 함께 본다: 기대추출 재현율(대본에서 뽑혀야 할
농작업·병해충·제품이 실제로 뽑혔는가, 분모 40)과 발생단계 정확도(병해충 발생단계가 정답
단계와 일치하는가). 개선을 수락하는 조건은 "종합점수가 노이즈 밴드(0.02)를 넘게 오르고,
결정적 지표와 faithfulness·chatter가 하나도 떨어지지 않을 것" — 즉 **없는 말을 지어내는 대가로
얻은 점수는 받지 않는다**.

## 2. STT 성능 — 감점 원인이 아니다

다섯 케이스 모두 화자 역할(농가/컨설턴트) 식별은 정확했고(5/5), 문자 오류율(CER) 평균은
0.131이다. WER 0.319는 대본 낭독 중 애드리브가 섞인 값이라 참고치다. 더 중요한 지표는
**도메인 핵심어(상표명·병해충명) 인식률 0.95** — 영농일지의 품질을 좌우하는 건 일반 문장이
아니라 이 단어들이기 때문이다.

| 케이스 | CER | 핵심어 | 비고 (근사 = 유사도 85 이상으로 잡힘) |
|---|---|---|---|
| `strawberry_botrytis_choice` | 0.067 | 1.00 | 전부 정확 (사파이어·점박이응애) |
| `strawberry_microbial` | 0.138 | 0.75 | **미인식**: 크린캡 → "크린 프린트 비용" |
| `strawberry_nursery_disinfect` | 0.165 | 1.00 | 근사: 다코닐·마쿠피카·엑설트·파밤나방 |
| `strawberry_planting` | 0.139 | 1.00 | 근사: 이리응애·시들음병 |
| `tomato_harvest` | 0.144 | 1.00 | 전부 정확 (검객·담배가루이) |

이번 평가에서 judge가 감점 원인을 귀속한 결과 **STT 귀속 감점은 0건**이다. 진짜 STT 실패는
전 케이스를 통틀어 "크린캡" 한 단어뿐이고, 나머지 오류는 근사 표기라 매핑 단계(동의어·퍼지
매칭)가 흡수한다. 즉 현재 품질 병목은 STT가 아니라 생성 쪽이며, 이는 "게이트웨이 STT를 더
고치는 것보다 추출·매핑·렌더를 고치는 게 우선"이라는 판단의 근거다.

## 3. 생성 성능 — 무엇이 점수를 올렸나

이번 세션 전까지 자가 개선 루프(프롬프트·매핑 데이터만 수정 가능)는 5회 연속 거부로 정체돼
있었다. 루프가 스스로 남긴 진단은 "**프롬프트는 사실을 더 담게 할 수는 있어도, 담을 칸을
만들지는 못한다**" — 그래서 이번에는 루프 밖에서 **스키마·매핑·렌더 코드 3건**(제안서 001)을
바꿨고, 각 단계를 같은 수락 기준으로 측정해 전부 통과시켰다.

| 단계 | 커밋 | 종합점수 | 발생단계 |
|---|---|---|---|
| 기준선 (프롬프트 루프 정체 시점) | — | 0.7800 | 0.667 |
| ① 발생단계·이름매칭 분리 | `0e1fb67` | 0.8467 (▲0.067) | 0.867 |
| ② 시점(when)을 1급 축으로 | `0d11b74` | 0.8533 (▲0.007) | 0.933 |
| ③ 기타 기록사항 = 잔여 사실 싱크 | `0f37e2f` | **0.9033** (▲0.050) | 1.000 |

> 각 단계는 STT 전사를 동결한 채 파이프라인+judge×3로 재측정. 재현율 0.900과 chatter 5.0은
> 전 구간 유지 — 점수를 사려고 정확도를 팔지 않았다는 뜻이다.

### ① 병해충 발생단계를 이름 매칭과 분리 (+0.067)

발생단계(예: "30%미만 (경고)")는 이미 옳게 계산되고 있었는데, 병해충 *이름*이 표준 목록에
없으면 계산 결과까지 통째로 버려져 "확인 필요"로 찍혔다. 단계 눈금은 모든 병해충에서
동일하다는 사실을 이용해, 이름 미매칭이어도 단계는 채우되 표준 코드는 비워 두고
`[표준 목록 미매핑]` 배지와 경고를 남기게 했다. farmos에 저장되는 prefill에는 코드 없는 행이
들어가지 않아 데이터 오염이 없다. 발생단계 정확도 0.667 → 0.867.

### ② 시점(when)을 사실 스키마의 1급 축으로 (+0.007, 오배치 소멸)

"지난주에 엑설트 살포"의 *지난주*를 담을 칸이 스키마에 없어서, 과거 작업이 엉뚱하게
**향후 작업·확인 계획** 섹션에 "(다른 날짜) 약제살포"로 올라가던 구조를 바로잡았다. 작업에
`ongoing`(계속 중) 값을, 제품에 `date_hint`(시점 원문) 필드를 신설하고, 과거 작업을 미래
섹션으로 보내던 렌더 분기를 삭제했다. 결과: 방제이력에 "엑셀트 (지난주 살포)", 체크리스트에
"[x] 관수 (계속)"가 찍히고, "(다른 날짜)" 오배치 줄들이 사라졌다.

### ③ 기타 기록사항을 "잔여 사실 싱크"로 (+0.050)

자유 서술 칸(기타 기록사항)의 입력이 통화 사실 *전체*였기 때문에, 향후 계획 섹션이 이미 쓴
내용을 산문으로 또 쓰고(중복), 잡담이 섞이고(chatter), 정작 "잎에서 흘러내릴 정도로 살포",
"엑설트 효과는 그냥 그랬다" 같은 부가 서술은 담을 칸이 없어 사라졌다. 제품·병해충에
`note`(그 사실에 묶인 부가 서술) 슬롯을 만들고, 입력 집합을 코드로 계산해(`residual_facts`)
다른 섹션이 렌더하는 것은 아예 입력에서 제외했다. **사실에 붙지 않는 잡담은 담을 칸 자체가
없다** — chatter가 프롬프트 지시가 아니라 구조로 차단된다. coverage +0.4, classification +0.8,
chatter 5.0 회복.

| 축 | 기준 | 최종 | 의미 |
|---|---|---|---|
| coverage | 3.40 | 3.40 | 정답 일지의 내용을 얼마나 담았나 |

| severity | 3.80 | 5.00 ▲1.2 | 병해충 발생단계 표기 |
| chatter | 5.00 | 5.00 | 잡담이 일지에 새지 않았나 |
| format | 4.00 | 4.40 ▲0.4 | 섹션 구성·표기 규칙 |

## 4. 자가 개선 루프 — 8회 전부 거부, 그리고 그 의미

프롬프트·매핑 데이터만 고칠 수 있는 자동 루프는 총 8회(구조 변경 전 5회 + 후 3회) 돌았고
전부 거부됐다. 실패가 아니라 **가드가 설계대로 작동한 기록**이다 — 8회 모두 타깃 감점은
줄였지만, 그 대가로 faithfulness·chatter·재현율 중 하나를 깎았기 때문에 수락되지 않았다.

| # | 타깃 | 타깃 결과 | 거부 사유 |
|---|---|---|---|
| 1~5 | 기타 기록사항·투입 제품·향후 계획 (구조 변경 전) | 모두 감소 | 종합 정체 또는 재현율·faithfulness·chatter 하락 → **구조 제안서 001 작성** |
| 6 | 투입 제품 누락 (11건) | 11 → 4 | faithfulness 4.4 → 4.0 |
| 7 | 향후 계획 누락 (8건) | 8 → 0 | 종합 0.884 — 발생단계·judge 동반 하락 |
| 8 | 방제이력 누락 (6건) | 정체 | faithfulness 4.4 → 3.8 (종합은 0.911로 올랐으나 기각) |

> **이 시스템의 핵심 동작 원리가 여기 있다.** 루프가 정체하면 그 거부 기록 자체가 "프롬프트로
> 안 되는 이유"의 데이터가 되고, 그것이 구조 제안서(`docs/proposals/001`)가 됐으며, 그 구조
> 변경이 +0.123을 만들었다. #6~#8의 거부 사유도 같은 방식으로 다음 구조 변경 후보를 가리키고
> 있다. 상세 기록: `docs/eval-journal.md`.

## 5. 남은 한계와 다음 후보

- **botrytis 케이스의 faithfulness(2)** — 최저 케이스. 언급만 되고 쓰지 않은 약제의 처리
  (거부 이유 서술)가 여전히 흔들린다.
- **방제이력의 2차 방제 대상** — 한 약제가 두 병해충을 겸할 때 두 번째 대상을 담을 칸이 없다
  (#8의 거부가 가리키는 지점 — 스키마 변경 후보).
- **향후 계획의 advice 경로** — 컨설턴트의 지속 관리 권고는 advice로만 남아 일지에 렌더되지
  않는다 (#7 — 렌더 경로 변경 후보).
- **제품 카테고리 오분류** — 천적(이리응애)·나노아이가 [농자재] 대신 [기타]로. 카테고리는 LLM
  선택이 그대로 렌더되는 구조라 기준표 신설이 후보다.
- **추출 변동성** — 같은 코드로도 실행마다 발생단계가 0.867~1.0으로 흔들린다. 판정은 반드시
  judge×3 + 짝지은 기준 재측정으로 해야 한다.

## 6. 재현 방법

```bash
# 전체 평가 (STT 포함, 최초 1회)
python -m app.agents.voice_eval --audio-dir ~/Downloads/recordings

# 코드/프롬프트 수정 후 재측정 (전사 동결 — --force stt 금지)
python -m app.agents.voice_eval --stages pipeline,judge --judge-repeat 3 --no-gate

# 자가 개선 루프
python -m app.agents.voice_eval.optimize --max-iters 3
```

결과물: `out/voice-eval/report.md`(집계) · 케이스별 `diary_*.md`(생성 일지) ·
`docs/eval-journal.md`(루프 기록). 이번 세션의 변경은 `eval/structural-001` 브랜치
3커밋(`0e1fb67` → `0d11b74` → `0f37e2f`)이며 main 반영 여부는 검토 후 결정한다.
